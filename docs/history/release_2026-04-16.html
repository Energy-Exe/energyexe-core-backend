1. What shipped & why it matters

This release implements the full Asset Prioritisation spec end‑to‑end: a quantitative engine that converts raw hourly generation, wind, and price data into a ranked list of commercial opportunities per windfarm — e.g. "this asset is losing ~€180k/yr to seasonal performance gaps with a confirmed structural cause".

Before this release we could see data. After this release we can see actions.

State today (2026‑04‑16): 360 windfarms with full pipeline data (98 first pass + 131 retried + 131 re‑processed after the root‑cause fix). 404 opportunities currently active.

2. The 6‑module performance pipeline

Each module is a class in app/services/. The orchestrator (PerformancePipelineService) walks them in order, sharing a single in‑memory hourly DataFrame so we don't re‑query the database per stage.

▼ per windfarm _load_hourly_data — ONE SQL pull (gen + weather + price) ▼ ┌─ Module 1 — Hard plausibility filters (wind, p_pu range) │ ├ Module 2 — Bin statistics → yearly raw curves │ → flag overperformance → capability curves │ → overall_clean curve [→ power_curve_bins] │ ├ Module 3 — Classify each hour vs capability curve │ → underperf / overperf / normal │ → lost_mwh, lost_eur, run grouping │ → monthly & yearly ODI [→ performance_anomalies, │ performance_summaries] │ ├ Module 4 — norm_ratio = actual_mw / expected_mw │ → monthly & yearly index vs long‑run mean │ [→ performance_summaries] │ ├ Module 5 — OLS trend on monthly residuals (operational wind 4–14 m/s) │ → slope %/yr, R², p‑value, 95% CI │ [→ degradation_results] │ └ Module 6 — Constraint proxy, PPA scenarios [→ performance_summaries]

Module 1 — Data cleaning

Hard plausibility filters drop physically impossible rows before any statistics are computed. The thresholds are conservative on purpose — we want to remove sensor errors and capacity breaches without hiding real underperformance.

VariableAllowed rangeComment
wind_speed0–40 m/sAbove 40 m/s = sensor fault or storm shutdown
p_pu (= MWh / rated MW)−0.05 to 1.20Slight negatives allowed (auxiliary load); >1.20 = data error
For curve building2–25 m/s windBelow 2 m/s and above 25 m/s are operational edge cases

Source: app/services/power_curve_service.py:25–35, 186–204

Module 2 — Empirical power curves

Wind speed is binned in 1.0 m/s steps. For each bin we compute q50, q90, mean, and MAD (median absolute deviation) of p_pu. Bins with fewer than 30 samples are dropped.

Three curve types are stored per windfarm:

  • raw — per year, before overperformance removal
  • capability — per year, after overperformance removal (used by Module 3)
  • overall_clean — one curve across all years (used by Modules 4, 6)

Overperformance flag (a row is dropped before capability/overall computation):

flag = (p_pu > q90_bin + 1.5 · MAD_bin) OR (p_pu > 1.02)

Source: app/services/power_curve_service.py:208–290

Module 3 — Anomaly detection & ODI

Every hour is classified against its year's capability curve:

ClassCondition
underperformancep_pu < q50_bin − 2.5 · MAD_bin
overperformancep_pu > q90_bin + 1.5 · MAD_bin OR p_pu > 1.02

For underperformance hours, loss is quantified as:

lost_mwh = max(0, q50_bin · rated_mw − actual_mwh) lost_eur = lost_mwh · (PPA price if active, else hourly market price)

Consecutive underperformance hours are grouped into runs (gap > 1h starts a new run, vectorised via diff().cumsum()). Runs ≥ 24h are counted as long runs — a strong signal of unattended outages.

Aggregates written to performance_summaries at month and year granularity:

  • odi_pct_underperf, odi_pct_loss_mwh, odi_pct_loss_eur
  • lost_mwh, expected_mwh, lost_eur, expected_revenue_eur
  • long_run_count, max_run_hours

Source: app/services/performance_anomaly_service.py

Module 4 — Wind normalisation

Strips out the question "was this year just less windy?" from the performance signal. For each hour with wind ≥ 4 m/s and a valid curve lookup:

norm_ratio = actual_mw / expected_mw expected_mw = curve_lookup[wind_bin] · rated_mw

Monthly average norm_ratio is then divided by the historical mean across all months and multiplied by 100. Index of 100 = long‑run average; >100 means the asset over‑delivered relative to its own history given that wind regime.

Both p50 and p10 reference variants are stored.

Source: app/services/wind_normalisation_service.py

Module 5 — Degradation analysis

Did the asset get worse over the last decade? Method:

  1. Filter to operational wind range (4–14 m/s) and bins where the reference is ≥ 0.10 p.u.
  2. Compute hourly residuals: p_pu − reference_curve_bin_p_pu.
  3. Aggregate to monthly mean residual.
  4. Fit OLS: residual ~ year_fraction (2020‑Jul = 2020.542).
  5. Report slope, R², p‑value, 95% CI — per q50 and q90 reference.

A statistically significant negative slope (e.g. −0.5%/yr, p‑value < 0.05) is the quantitative evidence behind degradation‑related opportunity flags.

Source: app/services/degradation_service.py

Module 6 — Commercial reporting

Two outputs:

Constraint proxy MWh: the energy not produced when the asset was at the P50 curve, summed across hours where the (q90 − q50) gap is positive. Read this as "upside that's been left on the table within the asset's own statistical envelope."

constraint_proxy_mwh = Σ (q90_bin − q50_bin) · rated_mw · hours lost_value_eur = constraint_proxy_mwh · avg_market_price

PPA scenarios (POST /performance-pipeline/ppa-scenarios/{wf_id}): sweep a list of EUR/MWh prices, return revenue, gap vs P50 target, and the value of a 1% performance lift at each price — useful for sales/AM conversations.

Source: app/services/performance_pipeline_service.py:197–352

3. Opportunity detection — 6 schemas

The pipeline outputs feed a detector that creates Opportunity rows when patterns of concern emerge. Each opportunity has a schema (what kind), a severity (CONFIRMED INDICATIVE WATCH), a branch (root‑cause hypothesis A/B/C), and a JSONB blob of computed data_slots + a list of missing_slots that would strengthen the case if filled.

SchemaWhat it flagsTrigger
OPS‑01 Volatile DisruptionsMonths where ODI is below threshold — outage / sensor / control episodes3+ low months = CONFIRMED, 2 = INDICATIVE, 1 = WATCH
OPS‑02 Performance SeasonalityCapacity factor in low‑wind season > high‑wind season (an inversion)≥8 pp gap and 2+ years sustained = CONFIRMED
OPS‑03 Contract MisalignmentOPS‑01 fired AND PPA has no availability penalty — the operator has no skin in the gameOnly fires if OPS‑01 fired
MKT‑01 Low Capture RateAsset capture rate >5 pp below zone average>10 pp = CONFIRMED, 5–10 = INDICATIVE, 2–5 = WATCH
MKT‑02 Storage OpportunityMKT‑01 fired AND no BESS — case for adding storageOnly fires if MKT‑01 fired (currently downgraded due to missing BESS data)
MKT‑03 High CannibalisationCannibalisation index (= 1 / capture rate) trending upward≥1.20 + 2 years = CONFIRMED, ≥1.10 = INDICATIVE, ≥1.05 = WATCH

Severity, branch, suppression

  • Severity — how confident we are this is real and worth investigating now.
  • Branch (A/B/C) — which root‑cause hypothesis the data points at; helps a downstream agent decide what to investigate first.
  • Suppression — conditions that cancel a flag because the financial exposure is locked. E.g. a long‑dated fixed‑price PPA suppresses MKT‑01 and MKT‑03 because price risk is already hedged.
  • Graceful degradation — if a key input is missing (e.g. wind resource index), severity is downgraded rather than the opportunity being silently dropped, and the missing field is added to missing_slots.

Cross‑schema dependencies

OPS‑01 (volatile) MKT‑01 (low capture) MKT‑03 (cannibalisation) │ │ (independent) └→ OPS‑03 (contract mis) └→ MKT‑02 (storage case)

The active opportunity per (windfarm_id, schema_code) is unique (partial unique index WHERE status = 'ACTIVE'). Re‑running detection supersedes the prior active row instead of duplicating it.

Source: app/services/opportunity_detection_service.py (single ~880‑line file containing all 6 schemas + pure‑static helpers for severity/branch/suppression)

5. The "Phantom OK" backfill story

The first end‑to‑end run processed 1,468 windfarms in ~8.6 hours. 1,168 hit NaN wind data (separate issue, see remaining‑work doc), but a smaller, more puzzling failure emerged: 121 windfarms logged success with full result counts — yet zero rows landed in the database for them.

Root cause: a single multi‑source SQL join

The original _load_hourly_data joined three tables in one query: 

SELECT g.hour, g.generation_mwh, w.wind_speed_100m, p.day_ahead_price
FROM generation_data g
LEFT JOIN weather_data w ON w.hour = g.hour AND w.windfarm_id = g.windfarm_id
LEFT JOIN price_data   p ON p.hour = g.hour AND p.windfarm_id = g.windfarm_id
WHERE g.windfarm_id = :wf_id;

On UK windfarms with multiple generation_units per windfarm and multiple price sources per hour (ENTSOE + ELEXON), the join Cartesian‑exploded: the same hour was emitted up to 6×. Subsequent INSERTs into performance_anomalies tripped the uq_perf_anomaly_wf_hour constraint — a UniqueViolationError. asyncpg's transaction was silently aborted, so:

  • The job code's try/except didn't see anything — the error fired during commit, not during business logic.
  • The logger.info("OK ...") line had already executed.
  • The connection pool returned a poisoned connection to the next windfarm in the same worker.

And the planner had its own problems: when wide enough joins were attempted on full‑history windfarms, EXPLAIN estimated 1.37 billion rows and the query stalled past 15 minutes.

The fix

Replace the 3‑way join with three single‑table aggregations + pandas merge. Each sub‑query is a single windfarm_id index scan with a GROUP BY hour: 

# 1) Generation — aggregate across units
SELECT hour,
       SUM(generation_mwh) AS generation_mwh,
       BOOL_OR(is_ramp_up) AS any_ramp_up
FROM generation_data
WHERE windfarm_id = :wf_id
GROUP BY hour HAVING BOOL_OR(is_ramp_up) = false

# 2) Weather — AVG across duplicates
SELECT hour, AVG(wind_speed_100m) AS wind_speed
FROM weather_data WHERE windfarm_id = :wf_id GROUP BY hour

# 3) Price — AVG across sources
SELECT hour, AVG(day_ahead_price) AS market_price
FROM price_data WHERE windfarm_id = :wf_id GROUP BY hour

# Then in pandas:
df = df_gen.merge(df_wx, on="hour", how="inner") \
           .merge(df_px, on="hour", how="left")

Other defensive changes that landed in the same PR:

  • Per‑module SAVEPOINTs via self.db.begin_nested() — one bad year of anomaly detection no longer poisons the whole pipeline transaction.
  • Bulk INSERT ... ON CONFLICT DO UPDATE in _store_summaries / _store_normalisation / commercial update — cuts ~780 round‑trips per windfarm to ~4.
  • Vectorised assign_run_ids with diff()/cumsum() — replaced a Python loop.
  • Widened degradation_results numeric precision — an OLS intercept of (−slope · 2020) overflowed Numeric(8,6).
  • Final await db.flush() at the end of run_pipeline — surfaces any remaining issue loudly instead of silently rolling back at commit time.
After the fix, all 131 windfarms re‑processed cleanly. DB now has 360 windfarms with full pipeline data, 40k power curve bins, 954k anomaly rows, 15k summary rows, 253 degradation results.

6. Frontend — opportunities UI

A new route at /opportunities (src/routes/_protected/opportunities/index.tsx):

  • Three summary cards at the top: counts of CONFIRMED / INDICATIVE / WATCH (across all matching, not just current page).
  • Filters: schema, severity, status (default excludes SUPERSEDED).
  • Manual trigger: "Run Detection" button hits POST /opportunities/detect and toasts the result.
  • Expandable rows: each row shows the windfarm, schema label, severity badge, branch, status. Clicking expands to show data_slots as a key‑value grid and missing_slots as small badges.
  • Lifecycle: in‑line "Acknowledge" and "Resolve" buttons call PATCH /opportunities/{id}.

API client lives in src/lib/opportunities-api.ts — thin wrapper over the existing apiClient with typed responses.
